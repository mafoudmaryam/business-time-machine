# Business Time Machine

Master's thesis project: an AI-assisted decision simulator for small food-service businesses (café, restaurant, bakery). An owner describes a decision in plain language ("raise prices 10% in March"). Claude turns it into structured parameters, the user confirms them, and a deterministic plus Monte Carlo engine projects revenue, profit, cash and customers for 12–36 months, compared against a baseline.

Thesis question: does AI-assisted simulation help non-expert owners compare the consequences of decisions before committing?

## Golden rules
1. **The LLM never computes numbers.** It only (a) turns text into `Decision` objects that are validated against `DECISIONS_JSON_SCHEMA` and (b) explains results using the engine's output. Every number comes from `engine/btm_engine`.
2. **Human in the loop:** the user confirms the parameters the LLM extracted before any simulation runs.
3. **The engine stays standalone:** no web or database imports inside `engine/btm_engine`.
4. **Reproducibility:** store `engine_version`, `seed` and `iterations` with every run.
5. **Scope:** small food-service businesses -- café, restaurant, bakery (`btm_engine/templates/`) -- six decision types (price, hiring, marketing, hours, menu, investment). Push back on scope creep.
6. Keep all tests passing (`cd engine && python -m pytest`). Add tests with every feature.

Three industry templates ship in `btm_engine/templates/` (`cafe`, `restaurant`, `bakery`) behind a `get_template(id)`/`list_industries()` registry -- café is the original, literature-sourced template; restaurant/bakery defaults are typical-small-business estimates with inline TODO/assumption comments, not yet calibrated.

Every business has its own currency (any ISO 4217 code, USD default), formatted everywhere with `Intl.NumberFormat` -- nothing is hard-coded to one currency symbol. `NumberField` (`src/components/NumberField.tsx`) allows an empty/in-progress value while typing and validates only on Next/Save, never forcing a 0. User-facing text avoids jargon -- no FTE, COGS, churn, p10/p50/p90 or "baseline"; instead "full-time staff", "ingredient costs", "regulars who stop coming", "bad case/most likely/good case", "if you change nothing" -- with a "?" tooltip next to every input and chart (`src/components/InfoTip.tsx`).

"Duplicate as new version" counts v2, v3, v4... (`nextVersionName`). Cash-risk alerts say "in N of 10 futures", never a percentage chance.

- `start.ps1` / `stop.ps1` at the repo root start and stop both dev servers together.

- **AI coach (phase 4) is built.** After a simulation, a friendly coach explains WHAT happens, WHY, what to WATCH OUT for, and IDEAS TO TRY, in plain words and the business's own industry words and currency.
  - Engine: `btm_engine/explain.py` -- `profit_breakdown` splits the profit difference vs "if you change nothing" into six drivers (price per sale, visits, ingredient costs, staff costs, marketing and fixed costs, investment and loan) that add up exactly (midpoint rule, tested), `key_moments` (full month, biggest regulars drop, lowest cash, overtake/fall-behind month), and `build_facts`, the compact rounded facts JSON (3 significant figures, uncertainty as "X of 10 futures"). It re-runs the central deterministic run, since the DB stores only bands.
  - Backend (`backend/app/coach/`): providers `template` (default, rule-based, also the automatic fallback), `ollama` (local, `OLLAMA_MODEL` default `qwen2.5:7b`; `qwen2.5:3b` is faster; keep_alive 30m, num_predict 450, num_ctx 4096), `anthropic` (needs `ANTHROPIC_API_KEY`; `ANTHROPIC_MODEL` default `claude-sonnet-5-5`, official SDK). Set in `backend/.env` (see `.env.example`): `COACH_PROVIDER`, `COACH_ENABLED` (off for the no-coach study group), `COACH_SHOW_MODE` (default false; the mode label is hidden from study participants). Endpoints: `GET /coach/status`, `POST /simulation_runs/{id}/coach` (cached per run in `coach_results`; `?regenerate=true`), `POST /simulation_runs/{id}/ask`. **Grounding check** (`grounding.py`): every number in the AI text must appear in the facts (6% rounding tolerance); on failure retry once, then fall back to the template. The AI writes only text plus idea title/why/decisions; ideas are validated against `DECISIONS_JSON_SCHEMA` and the engine's rules (invalid ones dropped, ideas repeating a lever the scenario already uses dropped, topped up to at least 2 from rule-based ideas), then each is simulated on the run's own seed, and **all numbers on an idea card come from that engine simulation**. Every provider call, retry, fallback and "ask" is logged in `ai_interactions` (prompt, response, tokens, duration, grounding result) -- thesis data. Tests mock every provider; `tests/conftest.py` pins the coach to `template` so a developer's `.env` never leaks into tests.
  - Frontend: `CoachCard` at the top of Compare and reopened runs (starts immediately after a simulation, "Your coach is reading the results…", friendly errors with retry, idea cards with "Try this idea" which opens the scenario builder prefilled with the parent scenario plus the idea, all decisions still unconfirmed, "Ask the coach" box, a single small "not financial advice" footer).
  - Measured on the developer's CPU-only laptop, one coach call (warm model): `qwen2.5:3b` about 50 s, `qwen2.5:7b` about 78 s; cold start (model loading) 80 s / 177 s. 7b writes better prose; 3b sometimes misreads a true number (grounding checks that a number exists in the facts, not that it is used correctly). `OLLAMA_TIMEOUT` defaults to 300 s; on timeout the rule-based coach takes over.
  - Coach wording rules (all tested): money is written the way the app shows it (`$27,900`, `format_money` in the engine; the AI is shown pre-formatted amounts and no bare currency code), regulars changes are a whole count or whole percent (never `3.01%`), the headline is a number-free verdict and the first sentence of the story never repeats it, and near-duplicate ideas (same lever, sizes less than 2x apart) are dropped (`coach/ideas.py`). `profit_breakdown` has seven drivers: price and menu are separate (a menu change of +8% on the average sale used to be lumped into "price per sale", which made a Price +10% plus menu +8% scenario show about 225,000 for price; the arithmetic was right, the label was not). While the AI writes, the card shows a calm "Your coach is adding more detail…" line and then fades in the AI version with an "Updated with more detail" tag; no timer.
  - **The coach never blocks a request.** `POST /simulation_runs/{id}/coach` returns at once with the rule-based version (`ai_status: "pending"`) and starts the AI in a background job (one worker thread, so a local model handles one run at a time); the frontend polls `GET /simulation_runs/{id}/coach` every 3 s, shows a calm progress line, and swaps in the AI version when `ai_status` becomes `done`. If the AI fails or times out (`failed`) the rule-based version simply stays, with no error screen; a `pending` left over from a server restart is turned into `failed` on the next read. Why this exists: the old design held one HTTP request open for the whole AI call, and React StrictMode (dev) fires effects twice, so a few Runs in a row filled the browser's 6-connections-per-host limit and the next simulate request queued behind coach requests ("RUNNING…" for minutes). `ask` is still a synchronous request. Test: `test_simulate_and_coach_start_stay_fast_while_the_ai_is_slow`.
  - Coach card (redesigned): verdict badge + short headline, three "now -> later" tiles (profit a month, cash, customers) with text trend labels (a change under 3% is a neutral grey "About the same"), up to four true-scale green/red "Why?" bars, one "Watch out" line only for a real risk, compact idea cards (one idea per area: price / menu or marketing / costs or hours, skipping areas the scenario already uses), and the full story behind "Read the full story". Inline SVG icons, no emoji; lining numerals. The verdict, tiles, bars and risk line are rule-based (`coach/summary.py`); old cached coach results get a summary rebuilt from the run's data (`_upgrade_old_payload`).
  - Not built: SSE streaming of explanations.
- **Claim consistency check** (`coach/consistency.py`, run inside `_generate` after the grounding check, for the coach card AND Ask): grounding only proves numbers exist, so this compares the AI's risk claims with the engine's facts. It reads phrases (run out of cash, out of money, not enough cash, go under, below zero, lose/losing money, make a loss, danger / at risk; and "safe", "no risk", "will not run out", "won't lose money") with simple negation handling ("runs out in 0 of 10 futures" counts as a safe claim) and checks them against cash-out shares (`cash_runs_out_of_10`, lowest cash), loss facts (`profit_total`, most-likely and bad-case profit) and the summary's risk flag. A claimed risk the facts do not show, a false all-clear when they do, or a wrong "N of 10" rejects the AI text with NO retry: the rule-based version stays, and the reason is written to `ai_interactions.error` ("claim check: ...") and `grounding.claims_reason`. It reads phrases, not meaning, so it will miss unusual wording; the rule-based text is tested to pass it.
- **"Ask the coach" is non-blocking** (it used to hold one HTTP request open for the whole AI call: measured 85 s behind the coach's own AI job, 143-192 s in the logs). `POST /simulation_runs/{id}/ask` returns at once (~2 s, engine facts rebuilt) with a rule-based answer (`template.answer_with_match`: topics cash / watch-risk / customers / staff / price / marketing / why / profit, always from the facts, never an invented number) plus `ai_status`; `GET /asks/{id}` is polled every 3 s by `AskCoach` (chat bubbles, calm "Your coach is adding more detail..." line, "Updated with more detail" tag, stops after 60 s, friendly one-line error + "Try again"). The three chip questions never use the AI (`ai_status: none`). Other questions also start a background job (own worker, same grounding check, retry once) that may replace the instant answer; failure or timeout leaves the instant answer. If the rules cannot tell: "I can't answer that one yet. Try one of these:" + the chips (`answered: false`, `suggestions`). Table `coach_answers`. Grounding only checks that numbers exist in the facts, so a grounded AI answer can still contradict the facts (seen: "cash could run out in the first month" with 0 of 10 futures) - the instant rule-based answer is the reliable one.
- **Scenario builder "Confirm all"**: a bar above the steps ("N steps · M confirmed", a temporary-change pair counts as one step) with "Confirm all" -> "All confirmed"; saving an edited step confirms it; pressing Save with unconfirmed steps asks "Confirm all N steps and save?" (Confirm all and save / Go back, Esc = go back). The backend still refuses to simulate unconfirmed decisions. How each decision was confirmed is stored in `decisions.confirmed_via` (`one_by_one` | `confirm_all` | `confirm_all_on_save` | `edited` | `looks_right` from the Compare page's "Looks right") and counted in the `interpret_outcome` log (`confirmed_via`). The describe-it results use the same bar (no separate shortcut).

A scenario with unconfirmed decisions shows "Check & add" -> panel with the decisions in plain words -> "Looks right" (`POST /scenarios/{id}/confirm`, then ticks the card) or "Edit" (builder with `?duplicate=<id>`, opens it as a new version). Simulation still refuses unconfirmed decisions.
- **Plain-language decision input ("Describe it in your own words") is built.** The scenario builder has a box where the owner types e.g. "Raise prices 10% in March and hire a baker for the summer"; it becomes UNCONFIRMED recipe steps, each with the owner's matched words shown softly underneath, and questions when something is missing. The AI only translates words; every number still comes from the engine.
  - Backend (`backend/app/interpret/`): `POST /businesses/{id}/interpret {text, answers}`, `GET /interpretations/{id}` (poll), `POST /interpretations/{id}/outcome`. Same providers as the coach (`COACH_PROVIDER`): `template` is a regex parser (`template.py`, also the fallback), `ollama`/`anthropic` use `ai.py` (prompt + strict reply schema). An AI request returns `status: "pending"` at once and a background job fills it in (one worker); if the AI fails or times out the rules answer (`fallback`). The provider is only revealed when `COACH_SHOW_MODE` is on.
  - Pipeline: AI or rules produce `Draft`s (words as the owner said them), then `resolve.py` does ALL the work with plain code: timing words -> simulation months (`months.py`), units, the "for the summer" start + reversing end, questions for anything missing, validation against `DECISIONS_JSON_SCHEMA` + `Decision.validate`, and a plain sentence in the industry's words and currency. The AI never picks a month, converts a unit or adds numbers.
  - **Month rule (the contract):** simulation month 1 = NEXT calendar month (today 30 Sep 2026 -> month 1 = October 2026). A month name means its next occurrence, never the current month ("March" -> month 6, "September" -> month 12). Seasons are northern-hemisphere: summer = Jun-Aug, spring Mar-May, autumn Sep-Nov, winter Dec-Feb. Every step shows both, e.g. "March 2027 (month 6)". The engine has no end month, so a temporary change is TWO decisions (the change, then its exact reversal), shown to the owner as ONE grouped step ("Hire 1 baker, June -> August 2027"): only hiring and percentage changes to prices/marketing can be reversed; hours and absolute amounts ask a question instead.
  - Ask, don't guess: a missing or vague amount or timing becomes a question (with quick-answer chips for timing), never an invented value. "Spend $500 a month on Instagram" is read as $500 ON TOP of today's marketing (the sentence says so); a marketing budget "to $700" is the total. Out-of-scope requests (second shop, logo, delivery...) get a kind refusal plus the list of what can be simulated. The owner's text goes into the prompt as data inside `<owner_text>` tags (angle brackets stripped), replies must fit the schema, numbers and timing the AI returns must be the owner's own words or answers (an invented value, e.g. 5% for "raise prices a bit", becomes a question), a `source_quote` that is not really in the text is not shown (a whole-sentence quote is narrowed to that decision's own clause), and words the AI marks out of scope can never also become steps.
  - Thesis data: every call and retry is logged in `ai_interactions` (kind `interpret`: text, provider, model, prompt, output, tokens, duration, validation in `grounding`; `simulation_run_id` is now nullable, with `business_id`/`interpretation_id`/`input_text`). When the owner saves the scenario the frontend calls `/outcome`, which logs kind `interpret_outcome`: per decision unchanged / edited / removed, plus added by hand and how many were confirmed.
  - Evaluation set: `backend/tests/fixtures/interpret_cases.json` (48 hand-written cases: easy, multi-decision, seasonal, ambiguous, out-of-scope, typos, mixed, hard; three industries) and `backend/scripts/eval_interpret.py --provider template|ollama|anthropic [--model M] [--sample N] [--limit N]` (exact / partial match, correct question, correct refusal, average time; CSV in `backend/eval_results/`). Scoring lives in `app/interpret/evaluation.py`. The rule-based parser was written alongside the cases, so its score is optimistic; a fresh, held-out set is needed for a fair comparison in the thesis.
  - Frontend: `DescribeBox` (chips in the business's staff word and currency, friendly "Reading what you wrote..." line, polling, inline questions with quick answers, out-of-scope message), `DecisionList` (matched words under each step, grouped temporary changes, per-step Edit with the same sentence-style form; editing un-ticks), `lib/interpretView.ts`. Reading again replaces the earlier reading's steps but keeps steps added by hand. Saving logs the outcome (fire and forget).
- The model spec (equations, sources, validation plan) lives in a Claude Doc the user can share with you.
- Known issue: the marketing (α, γ) and word-of-mouth (β) parameters are uncalibrated and look too optimistic, and are currently reused unchanged across all three industries.

## Planned architecture
- `backend/`: Python FastAPI, PostgreSQL (results stored as JSONB), SQLAlchemy + Alembic, JWT auth. The engine runs inline, since 1,000 runs take about 0.1 s.
- `frontend/`: React + TypeScript + Vite, Recharts for the p10/p50/p90 band charts.
- AI layer: Claude API with tool use for NL → decisions, and grounded explanations that stream to the frontend over SSE. Log every call to the `ai_interactions` table, because that data feeds the evaluation chapter.
- `docker-compose.yml`: frontend, API, PostgreSQL.

Database tables: users, businesses, business_snapshots, scenarios (with parent_scenario_id for versioning), decisions (source user|ai, confirmed bool), simulation_runs (engine_version, seed, iterations, summary JSONB), simulation_results (metric, p10/p50/p90 arrays), ai_interactions, assumptions.
